# Testing Guide

Testing in `crank` projects is straightforward because of Crank's strict layer separation, Domain-Driven Design (DDD) aggregates, and `TxRepositories` Unit of Work pattern.

This guide explains how to write unit tests, integration tests, handle mocks, and run end-to-end (E2E) tests.

---

## 3-Tier Testing Architecture

```
        ┌───────────────────────────────────┐
        │        End-to-End (E2E)           │  Build binary + execute HTTP requests
        ├───────────────────────────────────┤
        │    Integration Tests (Database)   │  Live GORM / Postgres assertions
        ├───────────────────────────────────┤
        │   Unit Tests (Handlers & Domain)  │  Fast in-memory repos / mock UoW
        └───────────────────────────────────┘
```

---

## 1. Unit Testing Aggregates & Validation

Domain aggregates are pure Go structs with raw `uuid.UUID` identifiers. You can test constructor logic and aggregate rules without any mock libraries or database connections.

```go
func TestNewBook(t *testing.T) {
	book, err := domain.NewBook("Clean Code", 49.99)
	
	assert.NoError(t, err)
	assert.NotEqual(t, uuid.Nil, book.ID)
	assert.Equal(t, "Clean Code", book.Title)
	assert.Equal(t, 49.99, book.Price)
}

func TestNewBook_InvalidPrice(t *testing.T) {
	_, err := domain.NewBook("Invalid Book", -10.00)
	
	assert.Error(t, err)
	assert.Contains(t, err.Error(), "price must be positive")
}
```

## 2. Unit Testing HTTP Handlers (Echo v5)

Every HTTP handler generated by `crank make handler` or `crank make scaffold` comes with an adjacent `_test.go` file (when `--tests` is specified).

HTTP handlers rely on the `TxRepositories` Unit of Work interface, allowing you to inject in-memory repository implementations for ultra-fast, zero-dependency testing.

```go
func TestBookHandler_Create(t *testing.T) {
	// Setup Echo context & recorder
	e := echo.New()
	reqBody := `{"title":"Refactoring","price":55.00}`
	req := httptest.NewRequest(http.MethodPost, "/api/v1/books", strings.NewReader(reqBody))
	req.Header.Set(echo.HeaderContentType, echo.MIMEApplicationJSON)
	rec := httptest.NewRecorder()
	c := e.NewContext(req, rec)

	// Mock Unit of Work & Handler
	mockUow := uow.NewInMemoryUnitOfWork()
	handler := v1.NewBookHandler(mockUow)

	// Execute Handler
	err := handler.Create(c)

	// Assertions
	assert.NoError(t, err)
	assert.Equal(t, http.StatusCreated, rec.Code)
	assert.Contains(t, rec.Body.String(), "Refactoring")
}
```

## 3. Integration Testing Repositories (GORM)

GORM repositories implement domain interfaces directly without leaking ORM types to the application layer.

For database integration tests, use a real PostgreSQL test database or SQLite in-memory instance:

```go
func TestGormBookRepository_Save(t *testing.T) {
	db := testutils.SetupTestDB(t) // returns *gorm.DB initialized with migrations
	repo := gormrepo.NewBookRepository(db)
	ctx := context.Background()

	book, _ := domain.NewBook("Domain-Driven Design", 60.00)
	
	err := repo.Save(ctx, book)
	assert.NoError(t, err)

	found, err := repo.FindByID(ctx, book.ID)
	assert.NoError(t, err)
	assert.Equal(t, "Domain-Driven Design", found.Title)
}
```

## 4. Running Tests with Crank CLI

Crank wraps standard `go test` workflows with convenient options:

```bash
# Run unit test suite
crank test

# Run tests with verbose output
crank test -v

# Run tests for a specific package
crank test ./internal/adapters/http/web/v1/...

# Run with race detector enabled
crank test --race

# Run E2E integration test suite (builds binary & tests generated project)
crank test -tags e2e ./e2e/...
```

> [!NOTE]
> All generated test files use realistic sample data literals tailored to your field specifications (e.g. `Field.Sample` for aggregate types and `Field.DTOSample` for DTOs), guaranteeing request bodies satisfy generated validation tags automatically.
